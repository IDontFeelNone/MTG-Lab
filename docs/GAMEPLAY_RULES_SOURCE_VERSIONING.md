## Separate the questions before retaining a claim

| Question | Evidence needed | What it does not establish |
| --- | --- | --- |
| Where does Wizards designate its rules artifact? | First-party rules index/reference with a specific designation edge | Artifact bytes, effective date, complete history or permission |
| Which bytes were observed? | Exact artifact content hash/length and acquisition receipt | That the artifact is current, supersedes another artifact or incorporates a bulletin |
| Which rules release applies to a requested scope? | Explicit reviewed version/effective-date, designation, validity/supersession and scope closure | That any content may be retained, redistributed or executed |
| May an operation use a source? | Operation-specific authoritative permission evidence and conditions | Every other operation, provider, upstream layer or use scope |
| Are reviewed rules executable? | Separately governed projection/interpretation, semantic compatibility and owner authorization | Those gates are not implemented by this review lane |

Official authority, availability, source integrity, temporal applicability,
retention, redistribution, service use and AI export stay distinct. The date in a
filename, the most recent discovered date, a successful HTTP status, an internal
release identity or a source hash cannot replace the missing evidence.

## Authority model and source classes

The source contracts distinguish these classes explicitly:

| Source class | Role |
| --- | --- |
| `RULES_INDEX` | First-party discovery/designation evidence; not itself the Comprehensive Rules |
| `COMPREHENSIVE_RULES` | Primary general gameplay authority for an exact version/effective scope |
| `UPDATE_BULLETIN` | Describes changes and clarifications; incorporation must be demonstrated |
| `RELEASE_NOTES` | Set/Card clarification with explicit applicability |
| `RULES_BLOG` | Explanatory evidence; does not silently replace the primary rules |
| `ORACLE` | Separate future Card-text authority; no intake/projection implemented here |
| `FORMAT_POLICY` | Independent future banned/restricted/deck-policy domain |
| `PROJECT_AUTHORED_FICTIONAL` | Original public-safe test authority; no real-source permission claim |

When an update summary conflicts with a verified applicable official
Comprehensive Rules release, the Comprehensive Rules remain the primary general
rules authority. This does not permit ignoring an unresolved update or declaring
an older release current. A conflict remains explicit until the source chain and
applicability can be reviewed.

Source records bind issuer, source class, exact reference, claimed/verified title
and version where available, source-provided effective date, retrieval/observation
metadata, artifact identity where available, provenance and evidence state.
Unverified or missing fields remain absent/unknown. An internal content-addressed
release ID is not a fabricated official semantic version.

## Evidence states and identities

The review lane uses the following distinct evidence states:

- `VERIFIED_ARTIFACT`: exact acquired bytes are integrity-bound; authority and
  applicability still require their own bindings.
- `VERIFIED_METADATA_ONLY`: verified bounded metadata without a claim that the
  complete source artifact was retained or verified.
- `DISCOVERED_UNVERIFIED`: a lead/reference awaiting its required checks.
- `EVIDENCE_UNAVAILABLE`: an attempted evidence retrieval could not establish the
  requested content. It is neither permission nor prohibition.
- `AMBIGUOUS`: multiple unresolved interpretations/candidates remain.
- `SUPERSEDED`: an explicit reviewed relationship establishes replacement within
  the declared scope; an older date alone does not establish supersession.
- `CONFLICTING`: incompatible claims remain unresolved.

Different identities answer different questions: source/reference identity,
artifact byte identity, acquisition receipt identity, metadata/review record
identity, release identity, lineage identity and explicit selection identity.
They must not be collapsed into one generic snapshot hash. The existing
`GameplayRulesSnapshot` identity remains an executable fictional-kernel contract,
separate from all source-review identities.

Deterministic canonical serialization/hash bindings preserve relocation and exact
replay. Retained observation timestamps are factual inputs; a new wall-clock
rendering does not silently change historical truth. Review does not refresh a
changed artifact's hash, rewrite its effective date or silently rebind an old
selection to new bytes.

The implementation lives under `src/gameplay_rules/source_evidence/`. It reuses

### Review contracts and bounded provider API

The immutable metadata envelopes are `SourceReference`, `ReleaseCandidate`,
`SourceReview`, `EvidenceIndex` and `VersionSelection`. Their `.create`,
`.from_dict`, `.verify`, defensive `.to_dict` and `.identity` methods follow the
existing deterministic contract conventions. Every envelope explicitly remains
`metadata_only=true`, `admission_eligible=false` and
`projection_authorized=false`. A `SourceReview` is a reviewed annotation, not an
owner admission decision or authorization. Unknown source metadata stays null;
no fake official semantic version is supplied to fill a schema field.

`WizardsRulesMetadataProvider` in `gameplay_rules.source_evidence.intake` implements
the existing acquisition provider request/response seam. The caller builds an
explicit `rules-source` request with an official HTTPS URL and an explicit
`observed_at` timestamp. `retrieve` returns a metadata-only `ProviderResponse`
with empty payload; no raw body is passed to a store or registry.
The default bounds are 2,000,000 response bytes, three redirects and a 15-second
request timeout. Redirect destinations remain validated; there is no crawl,
document-link following or current-release selection in the provider.

Bounded HTML title/document-link extraction is discovery metadata. Effective date
and official version are recognized only from explicit source metadata, not from
filenames, incidental dates or the observer's assumption. PDF bytes may be hashed
transiently but are not extracted or retained. The default transport preserves the
existing proxy/CA configuration; failure produces a safe acquisition outcome,
not fabricated source metadata. Offline tests inject fictional transport.

## Release lineage, scope and selection

Lineage is append-only: a newly observed candidate B may bind `supersedes` to
candidate A's existing immutable identity; a new evidence-index/relationship graph
records the expanded known history. A is not rewritten to add B, recompute A's
identity or alter historical selections. Source-level reverse pointers can contain
only already known explicit references; an absent future pointer means “not yet
bound here,” not “this source can never be superseded.” Historical snapshots stay
interpretable under their original exact dependencies.

A release selection must be explicit, reviewed and scoped. Current, as-of and
set-release questions are different requests; they cannot be answered by picking
`max(date)` or trusting a filename.

`select_version(index, *, scope, as_of_date, release_id=None, review_id=None)`
returns an immutable `VersionSelection` review result. Every scope requires an
explicit ISO as-of date, and a positive result requires an explicitly selected
reviewed `SourceReview`; missing review is a blocked result. Supported scopes are
`current_designation`, `as_of_date` and `set_release`. The `release_id` argument
for the last scope is an explicitly declared set/release key, not a rule that
chooses a catalog release by name. It is rejected for the other scopes.

The dependency graph distinguishes:

```text
first-party rules index
    -- DESIGNATES --> exact rules artifact/release
                           -- compatible applicability --> requested scope
update bulletin / release notes
    -- change/incorporation evidence --> exact release relationship
explicit reviewed supersession / validity
    -- constrains --> current / as-of / set-release selection
permission evidence
    -- independently constrains --> each requested operation
```

A page can designate an artifact without verifying its bytes. Verifying bytes
cannot establish that the release incorporates a later update. A historical
release can remain a valid historical artifact while failing a current-release
request. Selecting release A before release B requires reviewed validity and
supersession/applicability; it is not inferred from dates alone.

The owner reported an apparent June 19, 2026 Comprehensive Rules PDF and later
Reality Fracture update-bulletin changes. Those are leads to reconcile, not facts
verified by this implementation. Neither that PDF's applicability nor the update's
contents, date, URL or incorporation may be invented. Unless first-party evidence
proves an applicable release and closes the later-update question, record
`CURRENT_RULES_RELEASE_NOT_VERIFIED`. Do not call the June artifact “current”
merely because it is the only artifact available to the reviewer.

Missing official index designation, missing effective/source version, conflicting
metadata, ambiguous candidates, missing artifact integrity, unresolved update
incorporation or unreviewed lineage blocks the requested release scope. No
fallback to a historical release or the fictional kernel is permitted.
