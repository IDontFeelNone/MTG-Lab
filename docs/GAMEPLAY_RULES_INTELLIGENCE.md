# Gameplay Rules & Interaction Intelligence Foundation

## Scope and Architecture v13 gate

This separately owner-authorized milestone implements **design, contracts, generic
implementation primitives and a fictional executable proof**, pending independent
Project Manager review. It fits Architecture v13 and Decision 017's existing
versioned-domain boundary; no Tier-0 change or Architecture v14 is required.
The future-domain analysis already separates structured gameplay knowledge from
catalog authority and other evidence. Decision 017 is unchanged.

**GAMEPLAY RULES** govern game actions, priority, costs, zones and transitions.
**PRODUCT RULES** govern Products, Packs, Slots, Print Sheets and collation.
[`RULES_ENGINE.md`](RULES_ENGINE.md), `src/repository/rules.py` and
`src/repository/rule_research.py` remain the unchanged Product Rules contracts.
Nothing in this milestone renames them, repurposes them or adds a pack simulator.

This is not complete Magic rules support. Every executable rule and Card semantic
in the proof is project-authored and fictional. There is no real Card integration,
Comprehensive Rules corpus ingestion, Oracle parser, provider acquisition, format
legality implementation, strategy engine or gameplay simulation.

## Public API and deterministic contracts

The package is `src/gameplay_rules/`. Immutable, versioned envelope types expose
`.create(body)`, `.from_dict(document)`, `.verify()`, `.identity` and defensive
`.to_dict()` representations. Creation supplies the contract version and a
content-derived identity; deserialization verifies the supplied identity rather
than refreshing it. Strict JSON loading rejects duplicate keys and non-finite
numbers. Validation rejects malformed references and contradictions.

```python
engine = GameplayRulesEngine(explicit_rules_snapshot, explicit_card_semantics)
result = engine.evaluate_action(state, action)
# Inspection does not mutate state or pay costs.
outcome = engine.apply_action(state, action)
# LEGAL -> GameTransition; otherwise the blocked LegalityResult.
replayed = engine.replay_transition(state, transition)
```

The caller supplies actual verified contract instances. There is no implicit
latest/current snapshot, repository lookup, network request or ambient catalog
fallback. The engine is local and pure with respect to its verified inputs.
Malformed/corrupt contracts and impossible bindings raise typed
`GameplayContractError`; valid but illegal, unknown or unsupported actions return
structured results.

| Contract | Content identity binds |
| --- | --- |
| `GameplayRulesSnapshot` | Game, explicit rules version/effective date, engine contract, source metadata, exact rule definitions/hashes, capability manifest and parameters |
| `CardGameplaySemantics` | Fictional Card identity, compatible exact rules snapshot, semantic version, sources, structured costs/timing/effects/restrictions, completeness and review status |
| `GameState` | Rules snapshot, revision, every declared player/object/zone/resource/priority/stack/outcome/unknown field |
| `GameAction` | Exact expected before-state, game, rules snapshot, actor, kind, object/ability/payment selection |
| `PaymentResult` | Exact cost/pool/plan/result and status under the configured deterministic payment order |
| `LegalityResult` | Request/state/snapshot, requirements, costs/payment, rule references, unsupported dimensions and structured explanation |
| `GameTransition` | Bound request/before-state, complete after-state, exact changes and rule references |

Canonical JSON and domain-separated SHA-256 identities exclude machine paths,
wall-clock build times and randomness. Rule-source retrieval/effective dates are
retained factual inputs; a fresh rendering time is not an analytical input.
Relocation of identical fictional inputs preserves their identities and results.

## Rule authority, evidence and versioning

Rules are versioned evidence, not whatever happens to be installed. Source
metadata can distinguish:

- official comprehensive rules;
- official Oracle/card text;
- official rulings/release notes;
- format/banned-restricted policy; and
- project-authored fictional/test rules.

Each source records a game, stable source identity/class, issuer/title, exact
URL/reference, effective and retrieved/observed dates, available content hash,
revision, supersedes/superseded-by relationships, provenance, retention status,
permission/evidence status and completeness. These source classes are not
interchangeable. For future Magic support the official Comprehensive Rules are
the primary general gameplay authority; update bulletins and release notes are
change/clarification evidence, not an automatic conflicting replacement.
Official Card text, rulings and format policy remain distinct inputs.

`GameplayRulesSnapshot` binds an explicit rules version and effective date,
`gameplay-kernel-v1`, the `fictional-two-player-v1` execution profile, source
identities, every included rule and rule hash, capabilities and unsupported rule
families. Rule references carry a stable internal rule ID, optional external
number/reference, exact rules snapshot/source, category, bounded summary and
status. Explanations need not copy an entire source document.

The implemented execution profile permits project-authored fictional rules only.
Metadata about an official source does not make that source executable or permit
its content to be redistributed. An incompatible game, rules snapshot, engine
contract, semantic binding or changed rule/capability hash fails closed. There is
no automatic migration or fallback to a newer revision.

## GameState, zones and hidden information

`GameState` is immutable and content-addressed. It includes exactly two distinct
players, life (or explicitly unknown life), mana pools and land-play accounting;
active player, turn/revision, phase/step and priority player; explicit zones and
object membership; the stack in bottom-to-top order; consecutive passes; pending
system actions; game status/winner/loser identities; unknown fields and active
unmodeled effects.

Zones have identities distinct from their kinds. The vocabulary includes library,
hand, battlefield, graveyard, stack, exile and command. Zone metadata declares its
owner and visibility. An object's `zone_id` is its location authority; stack
membership must agree rather than creating a second contradictory location.
Objects retain owner/controller separately, optional Card/semantics identities,
known/unknown status and tapped/untapped/unknown state.

Hidden state is not filled from memory, names, random draws or an opponent's
unseen cards. Unneeded hidden objects may remain unknown; unknown information
required by an evaluated action produces INDETERMINATE. No library draw, shuffle
or information-reveal subsystem is implemented.

## Actions, requirements and explanations

Implemented player actions are `pass_priority`, `play_land`, `cast_spell` and
`activate_ability`. Implemented system actions are `resolve_top_of_stack`,
`perform_state_based_actions` and `advance_step_or_phase`. A system action has no
player actor and must match the exact pending boundary. Unknown action kinds are
UNSUPPORTED; invalidly shaped actions are contract errors.

`evaluate_action` returns one of:

| Status | Meaning |
| --- | --- |
| LEGAL | Every required implemented condition is satisfied on the exact known inputs |
| ILLEGAL | A known requirement fails, for example insufficient known mana or wrong timing |
| INDETERMINATE | Required information is unknown or an unknown relevant override could matter |
| UNSUPPORTED | The request requires a rule/cost/effect primitive not implemented by this profile |

The result contains action/before-state/snapshot IDs, satisfied/failed/unknown
requirements, structured rule references, costs and payment availability,
assumptions, unsupported dimensions, a deterministic explanation and result ID.
For example, a failed cast records an insufficient-mana requirement and the
fictional cost-payment/casting references. An unimplemented action family may
have no applicable rule citation; its snapshot and explicit coverage failure
remain bound without inventing an unrelated rule. The failed result remains an
explanation of what cannot currently be established, not a strategic suggestion.

Future AI may explain these validated structures with their citations and
omissions. AI prose, conversation memory, arbitrary text and provider content
never become executable rule authority. No AI transport or model call is added.

## Mana and costs

Costs are structured data. `plan_mana_payment` first reserves exact colored mana,
then pays generic mana by the explicit snapshot symbol order. The proof configures
fictional blue/red resources. A supplied payment plan must pay exactly the required
cost with available permitted symbols; no arbitrary overpayment or guessed source
is accepted. Payment results bind input cost, availability, paid amounts and
remaining resources. Inspecting payment does not mutate the pool.

Insufficient known mana is ILLEGAL; unknown availability is INDETERMINATE;
unsupported cost forms remain UNSUPPORTED. Hybrid, Phyrexian, snow, X, convoke,
delve, improvise, alternate costs, additional nonmana costs, reducers/increasers,
spend restrictions and mana-provenance restrictions are not implemented. The
engine never discards an unrecognized cost to declare a cast legal.

## Priority, timing, stack and turn boundary

Only the priority holder may take a priority-required player action. Fictional
sorcery timing requires the actor to be active, in the declared own main/action
step, with an empty stack. Fictional instant timing requires priority under this
profile. The land-play action uses the explicitly configured allowance and timing
conditions, moves hand to battlefield without stack use and increments usage.

A legal cast pays the known cost and moves the object from hand onto the stack.
Passing priority records the actor and transfers priority. Both players passing
clear priority and schedule state-based-action checking before stack resolution
or, for an empty stack, the step-advance boundary. Pending system actions must
finish before another player action. Resolution applies only authored supported
effects to the top object, records its configured zone move and schedules another
SBA checkpoint. The profile grants priority through its explicit system boundary;
it does not claim complete Magic priority or triggered-ability handling.

The declared beginning/main/ending sequence can advance deterministically and
wrap to the other active player, incrementing the turn and resetting declared
land accounting/resources. No real untap/draw/combat/end-cleanup rules are silently
added to that minimal boundary.

## Card semantics and future override seam

Mechanical Card evidence is separate from executable gameplay semantics.
Oracle text held by MechanicalCardIntelligence is not executable understanding.
`CardGameplaySemantics` is a separate versioned, review-bound concept with explicit
Card identity, exact compatible rules snapshot, source references, structured
costs/timing/abilities/effects/restrictions, completeness and unsupported text.
All current instances have `fictional_test_only` review status.

The current primitives interpret known structured data only: tap-mana production,
no-op, and controller/opponent life adjustment. There is no Oracle parser,
regex-based card classifier, LLM interpreter, arbitrary Python hook, `eval`,
embedded script or card-name-specific branch.

Base rules are not assumed immutable in the face of Card effects. State can
explicitly identify active unmodeled effects, affected actions and required
capabilities. Semantics can declare unsupported abilities/restrictions or partial
coverage. A relevant unknown permission/restriction, replacement/prevention,
continuous effect, layer/dependency or trigger prevents a confident base-rule
answer. Those families need separate reviewed primitives and precedence contracts;
this milestone does not implement the complete golden-rule/override system.

## Transitions, replay and SBA

`apply_action` reevaluates the exact request/state binding. Only a LEGAL result
produces a new `GameTransition`; blocked outcomes remain LegalityResult objects.
The input state is never mutated. A transition includes the complete bound action,
before/after IDs and after-state, actor, state/zone/resource/stack changes, rule
references and required system actions. Zone moves therefore have explicit
records rather than objects disappearing from one list and appearing elsewhere.

`replay_transition` verifies the exact before-state, action and rules snapshot and
reproduces the identical after-state/transition. Changed rule definitions, Card
semantics, capabilities or bindings fail rather than being refreshed. No clock,
network or random seed is needed by this proof.

The fictional SBA checkpoint checks known life against its configured threshold.
Loss/end is recorded deterministically; simultaneous qualifying losses produce a
draw. Unknown relevant life remains unknown. The rest of the real state-based
action rules are unsupported, not implied by this one example.
