# Rules Reasoning Composition V1

This read-only workflow answers: **do the declared ability's bounded mana-payment
timing conditions and an independently declared static resource pool jointly
support the proposed abstract payment question?** It combines two existing
analytical owners; it neither interprets Card text nor executes an activation.

## What is combined

1. [Real-Card Rules Reasoning V1](REAL_CARD_RULES_REASONING_V1.md) derives the
   bounded mana classification from explicit characteristics, assesses a declared
   payment opportunity, and tests the same-ability unresolved-activation restriction.
2. [Declared Resource Assignment V1](DECLARED_RESOURCE_ASSIGNMENT_V1.md) decides
   whether distinct physical copies in the complete declared pool can cover the
   simultaneous abstract demands. A flexible copy fills at most one job.
3. The composition reports both native results and their conjunction, with exact
   content identities, evidence references and an inspectable five-step trace.

Neither component alone answers this joint question. The composition supplies no
new rules or matching algorithm. In particular, timing permission does not create
resources; an assignment does not establish activation legality; classification
as a mana ability does not prove actual mana output.

## Closed input scope

Use the original [request](../tests/fixtures/rules_composition_v1/payment-pool.json).
`rules-reasoning-composition-input-v1` requires exactly `schema_version`,
`question`, `scenario_id`, `rules`, `resources` and `assumptions`.

- `question` is exactly `MANA_PAYMENT_TIMING_AND_STATIC_ASSIGNMENT`.
- `scenario_id` is printable, trimmed, 1–128 characters and must equal the native
  rules input's scenario identity. This binds a caller-declared scenario, not
  independent proof of a Card, game state or causal relationship.
- `rules` is the unchanged closed rules-reasoning input, including its exact
  retained-context identity and explicit unknown facts.
- `resources` is validated by the existing public resource validator and engine.
  The entire population must be observed: `cards_seen == population_size`.
  Native bounds therefore limit this composition to **1–20 declared physical
  cards**, at most two abstract kinds, demands 0–3 per kind and the native class
  and work limits. At least one demand must be positive.
- The resource question has no target requirement: minimum 0, mode `observe`,
  and all class target flags false. Target observation/reservation and partially
  sampled populations remain supported by their owning engine, outside this
  composition's scope. An empty physical pool is outside that engine's contract;
  no filler copies are invented.
- `assumptions` must exactly declare `pool=INDEPENDENTLY_DECLARED_STATIC_AVAILABILITY`,
  `demands=ABSTRACT_REQUIREMENTS_NOT_VERIFIED_MAGIC_COSTS`, and
  `ability_output=NOT_INFERRED_FROM_MANA_ABILITY_CLASSIFICATION`.

Sampling all physical copies gives exactly one possible physical hand. The native
engine's exact result is therefore 0/1 or 1/1, interpreted as static assignment
infeasibility or feasibility. The adapter reads that result; it performs no second
matching calculation. It does not reinterpret a positive draw-access probability
as present availability. Native demand/class/type validation remains authoritative.
Resource classes normalize using the existing owner, so valid row reordering
preserves composition identity.

## Conclusions and limits

`SUPPORTED_UNDER_DECLARATIONS` requires the native timing conclusion to apply,
the same-ability restriction to be absent, and exact static assignment to succeed.
`NOT_SUPPORTED_UNDER_DECLARATIONS` retains every known negative witness.
`UNRESOLVED` preserves unknown required timing facts when resources do not already
defeat the conjunction. A resource failure does not resolve unknown rules facts.

The report separately exposes classification, payment opportunity, same-ability
restriction, and static assignment. Native reports are retained without editing
their authority, evidence, inputs or limitations. Every result keeps activation
legality, actual resource generation/payment and current real-Card verification
unestablished, strategic usefulness unassessed, and execution blocked.

The original scenario declares a qualifying ability, a spell-casting mana-payment
request without priority, and two independently available flexible A-or-B copies
against A=1 and B=1. The joint answer is supported under those declarations,
even though the ability's declared current output is ZERO. The pool is not
generated by that ability. Replacing one flexible copy with a nonresource copy
makes assignment infeasible without changing the timing finding. A positive
target count excludes the mana timing exception even with ample resources.
An unresolved activation blocks repeating the same qualifying ability. Unknown
payment facts remain unresolved; contradictory targets or unsupported
self-replacement application produce structured refusals.

## API, CLI and reproduction

```python
import json
from pathlib import Path
from card_intelligence.rules_reasoning import CONTEXT_ID
from card_intelligence.rules_composition import load_rules_composition

consumer = load_rules_composition(review_root=Path('reference-reviews'),
                                  expected_context_id=CONTEXT_ID)
request = json.loads(Path('tests/fixtures/rules_composition_v1/payment-pool.json').read_bytes())
report = consumer.assess(request)
consumer.replay(report.to_json().encode())
```

```sh
PYTHONPATH=src python -m card_intelligence.rules_composition \
  --review-root reference-reviews \
  --expected-context-id sha256:59eb902055e8f597f9b0761ac176ad37406365c53a87098e3dcf621a1c5df478 \
  --json assess tests/fixtures/rules_composition_v1/payment-pool.json
```

Omit `--json` for readable output; `validate REPORT.json` recomputes both native
results. JSON follows the existing `card_rules_pilot.contract` canonical sorted
UTF-8 format with one trailing LF. Explicit caller-controlled redirection can save
the report; the consumer writes no files automatically.

Reports use `rules-reasoning-composition-report-v1`, owned immutable bytes and the
existing domain/content identity convention. They contain normalized exact
inputs, native component IDs/results, retained evidence bindings, missing facts,
unresolved dependencies and authority boundaries. Replay freshly revalidates
retained rules and recomputes every field; changing inputs or results fails even
after coherent rehashing. Selected packaged code hashes and native versions bind
compatibility and reject code-file drift under an imported process. Hashes do
not authenticate declarations, human review or permission.

The request limit is 24 KiB, report limit 64 KiB; native input and resource work
limits remain intact. Full-pool resource enumeration has one count vector.
Selected public code reads are capped at 512 KiB per fixed file. Unknown fields,
unsupported scopes/versions, contradictory facts, unavailable or altered evidence
and native resource refusals fail closed through `CompositionError.as_dict()`.
Refusals identify the component and are never converted into an impossible event
or partial authoritative result. CLI refusals use stderr and exit 2; calculated
positive, negative and unresolved reports use exit 0.

## Existing portable investigations

`consumer.record_reference(artifact, report, branch_id=..., parent_id=...,
metadata=...)` revalidates the composition and delegates to the existing
`workbench.investigations.append_revision`. It appends a **note-only** revision
with a qualifying content-hash reference. Caller metadata and old branches remain
unchanged; no ancestor deck result is inherited as current. Existing save,
reopen, lineage, explicit handoff selection and replay contracts stay unchanged.

Retain the full composition JSON beside the investigation. The existing
investigation format holds the reference, not a new embedded analytical type.
Its native replay verifies its own deck calculations and does not fetch or replay
external references. Replay the supplied composition separately through this
consumer and check its report identity against the selected revision. A readable
handoff labels the reference unverified; neither attaching it nor user-authored
notes establish an accepted research finding. No database, automatic saving,
source-bearing AI export or live ChatGPT connection is added.
